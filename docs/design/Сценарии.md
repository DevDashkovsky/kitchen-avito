# Бизнес-сценарии
## Успешное оформление и выполнение заказа
### Участники
- покупатель;
- Авито.Кухня;
- заведение.

### Шаги
1. Покупатель открывает Авито.Кухню и находит заведение или блюдо через список или поиск.
2. Покупатель открывает меню заведения и добавляет доступные блюда в корзину.
3. Покупатель передаёт имя, телефон, адрес доставки и позиции заказа с количеством и ожидаемой ценой.
4. Авито.Кухня проверяет, что все блюда принадлежат одному заведению, доступны, а их цены не изменились.
5. Авито.Кухня рассчитывает итоговую стоимость, создаёт заказ в статусе `pending_confirmation` и возвращает покупателю `tracking_token`.
6. Сервис заведения забирает новый заказ через партнёрский API и переводит его в `confirmed`.
7. Web-клиент периодически запрашивает заказ по `tracking_token` и показывает покупателю его текущий статус.
8. Заведение последовательно переводит заказ в `preparing`, `ready_for_delivery`, `delivering` и `completed`.

### Результат
Заказ доставлен покупателю, его статус - `completed`, а итоговая сумма заказа сохранена.

## Изменение цены или доступности при оформлении
### Участники
- покупатель;
- Авито.Кухня;
- заведение.

### Шаги
1. Покупатель добавляет блюда в корзину.
2. Заведение изменяет цену блюда или отмечает его недоступным через партнёрский API.
3. Покупатель отправляет заказ со старой ценой или с позицией, которая уже недоступна.
4. Авито.Кухня сравнивает данные корзины с актуальным меню.
5. Заказ не создаётся. API возвращает `409 Conflict` и список изменившихся позиций с актуальными данными.
6. Web-клиент сохраняет корзину и показывает покупателю, что именно изменилось.
7. Покупатель принимает новую цену либо удаляет недоступное блюдо, после чего может повторить оформление.

### Результат
Заказ не создаётся без явного согласия покупателя на изменения.

## Отклонение заказа заведением
### Участники
- покупатель;
- Авито.Кухня;
- заведение.

### Шаги
1. Авито.Кухня создаёт заказ в статусе `pending_confirmation`.
2. Сервис заведения получает новый заказ через polling партнёрского API.
3. Заведение обнаруживает, что не может выполнить заказ.
4. Заведение переводит заказ в `rejected` и передаёт обязательную причину отклонения.
5. Авито.Кухня проверяет переход и сохраняет статус и причину.
6. Web-клиент получает обновлённый заказ по `tracking_token` и показывает покупателю причину отклонения.

### Результат
Покупатель видит причину, почему заказ не принят. Заказ остаётся в конечном статусе `rejected`.

## Отказ после подтверждения
1. Заведение принимает заказ и начинает его выполнение.
2. В `confirmed`, `preparing` или `ready_for_delivery` выясняется, что выполнить заказ нельзя.
3. Заведение отправляет `rejected` с причиной; для `other` добавляет непустой комментарий.
4. API атомарно сохраняет отказ. Покупатель при следующем запросе статуса видит причину.
5. Валидный повтор возвращает `200` с первоначальной причиной, не меняя её и время изменения.

Если передача в доставку опередила отказ, API возвращает `409`; заказ остаётся
в `delivering`. Завершённый отказом заказ больше нельзя продвигать по статусам.
История этапа отказа, возврат денег и сбой доставки в MVP не моделируются.

## Заведение не ответило вовремя
### Участники
- покупатель;
- Авито.Кухня;
- заведение.

### Шаги
1. Авито.Кухня создаёт заказ в статусе `pending_confirmation`.
2. Заведение не подтверждает и не отклоняет заказ в течение двух минут.
3. По истечении таймаута Авито.Кухня переводит заказ в `rejected` с причиной `confirmation_timeout`.
4. Web-клиент получает обновлённый заказ по `tracking_token` и показывает покупателю, что заведение не ответило вовремя.
5. Попытка подтвердить заказ получает `409 Conflict`. Если срок истёк при попытке перехода, API записывает системный отказ и отвечает `409`. Валидный повтор `rejected` для уже отклонённого заказа получает `200` с сохранённой `confirmation_timeout`, без её замены.

### Результат
Покупатель получает понятный результат, а заказ остаётся в конечном статусе `rejected` с причиной `confirmation_timeout`.

## Отмена заказа покупателем
### Участники
- покупатель;
- Авито.Кухня;
- заведение.

### Шаги
1. Заказ находится в статусе `pending_confirmation`.
2. Покупатель отправляет запрос на отмену по `tracking_token`.
3. Авито.Кухня проверяет текущий статус заказа.
4. Если заведение ещё не подтвердило заказ, Авито.Кухня переводит его в `cancelled`.
5. Если заведение успело подтвердить заказ раньше, API возвращает `409 Conflict`, а статус не изменяется.
6. Заведение не может подтвердить уже отменённый заказ.

### Результат
Если отмена выполнена раньше подтверждения, заказ остаётся в конечном статусе `cancelled`. При одновременных запросах успевает только первый допустимый переход.

## Обновление меню заведением
### Участники
- Авито.Кухня;
- заведение.

### Шаги
1. Сервис заведения отправляет запрос с API-ключом.
2. Сервис заведения отправляет данные новой позиции меню или изменения существующей: категорию, название, описание, цену и доступность.
3. Авито.Кухня определяет заведение по API-ключу и проверяет переданные данные.
4. Изменения сохраняются в локальной копии меню Авито.Кухни.
5. Новые запросы покупателей получают обновлённые данные.
6. Если старые данные уже остались в корзине покупателя, расхождение обнаруживается при оформлении заказа.

### Результат
Заведение управляет своим меню без прямого доступа к базе Авито.Кухни, а покупатели видят актуальные данные.
