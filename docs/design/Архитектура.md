# Архитектура Go-кода
## Итоговая структура
```text
go.mod
go.sum

api/
  openapi.yaml

cmd/
  kitchen/
    main.go
  establishment/
    main.go

internal/
  kitchen/
    api/
      generate.go
      oapi-codegen.yaml
      openapi.gen.go
    config/
      config.go
    domain/
      establishment.go
      menu.go
      order.go
      errors.go
    handlers/
      handler.go
      middleware.go
      establishments.go
      menu.go
      orders.go
      mappers.go
      errors.go
    repository/
      repository.go
      establishments.go
      menu.go
      orders.go
    service/
      establishments.go
      menu.go
      orders.go
    worker/
      confirmation_timeout.go

  establishment/
    config/
      config.go
    kitchenapi/
      generate.go
      oapi-codegen.yaml
      client.gen.go
    worker/
      order_processor.go
```

Тесты размещаются рядом с проверяемым кодом в файлах `*_test.go`. Отдельный каталог `tests` не создаётся. Миграции, Docker Compose и остальные файлы запуска будут добавлены после отдельного проектирования соответствующих частей.

## Go-модуль и запускаемые приложения
В репозитории используется один Go-модуль и два независимо запускаемых приложения:

```text
cmd/
  kitchen/
  establishment/
```

`cmd/kitchen` содержит точку входа основного сервиса Авито.Кухни.

`cmd/establishment` содержит точку входа примера заведения, которое взаимодействует с основным сервисом через его API.

Один Go-модуль упрощает управление зависимостями, сборку Docker-образов и переиспользование сгенерированного API-клиента. Отдельные Go-модули для двух приложений в MVP не создаются.

В `go.mod` используется короткий локальный путь модуля и Go 1.25:

```go
module kitchen-api

go 1.25.0
```

Внутренние импорты начинаются с `kitchen-api/internal/...`. Длинный технический путь удалённого репозитория в module path не используется, поскольку проект собирается как приложение внутри своего репозитория и не публикуется как внешняя Go-библиотека.

## Точки входа
Каталоги `cmd/kitchen` и `cmd/establishment` содержат только точки входа приложений. Оба `main.go` загружают конфигурацию, создают зависимости и корректно завершают процесс по сигналу остановки.

`cmd/kitchen/main.go` запускает HTTP-сервер и timeout worker. `cmd/establishment/main.go` запускает только фоновую обработку заказов через клиент Авито.Кухни.

HTTP-обработчики, SQL-запросы и бизнес-правила в `cmd` не размещаются. Реализация приложений находится во внутренних пакетах репозитория.

## Границы приложений
Внутренний код основного сервиса и примера заведения разделяется по приложениям:

```text
internal/
  kitchen/
  establishment/
```

`internal/kitchen` содержит реализацию основного сервиса, а `internal/establishment` содержит реализацию примера интеграции заведения.

Общий пакет вроде `internal/common` заранее не создаётся. Если в процессе реализации появится действительно переиспользуемый код, для него будет выделен конкретный пакет с понятным назначением.

## Основные пакеты сервиса Авито.Кухни
Основной сервис использует следующую структуру:

```text
internal/kitchen/
  api/
  config/
  domain/
  handlers/
  repository/
  service/
  worker/
```

- `api` содержит сгенерированные из OpenAPI транспортные модели, strict server интерфейс и обвязку Chi;
- `config` загружает и проверяет настройки основного сервиса;
- `domain` содержит доменные модели и доменные ошибки;
- `handlers` реализует сгенерированный интерфейс, преобразует транспортные модели и вызывает сервисный слой;
- `service` содержит бизнес-логику приложения;
- `repository` выполняет операции с PostgreSQL;
- `worker` запускает фоновую обработку таймаута подтверждения.

Основной поток вызова: `handlers -> service -> repository`. Пакеты `service` и `repository` используют модели из `domain`. Сервисный и доменный код не зависят от HTTP-моделей из `api`, а зависимость сервисов от хранилища выражена их собственными интерфейсами.

Отдельный пакет `dto` не создаётся. Транспортными DTO служат модели, сгенерированные в `api`. Преобразование между ними и внутренними моделями выполняется в `handlers`.

## Доступ к PostgreSQL
Для рабочих запросов приложения используется нативный интерфейс `github.com/jackc/pgx/v5` и пул соединений `pgxpool`. ORM, `sqlc` и обёртка `database/sql` в MVP не используются.

Goose отвечает только за создание и изменение структуры базы через миграции. Репозиторный слой через `pgx` выполняет запросы во время работы приложения: чтение меню и заказов, создание заказов и изменение их статусов.

Репозиторный слой остаётся одним пакетом без дополнительного подпакета `postgres`:

```text
internal/kitchen/repository/
  repository.go
  establishments.go
  menu.go
  orders.go
```

В `repository.go` хранится общая структура репозитория с `*pgxpool.Pool`. Запросы разделяются по предметным областям между файлами одного пакета. Другие реализации хранилища в MVP не создаются.

## Доменный пакет
Доменные модели основного сервиса размещаются в одном пакете:

```text
internal/kitchen/domain/
  establishment.go
  menu.go
  order.go
  errors.go
```

Пакет содержит уже спроектированные сущности, статусы и доменные ошибки. Доменные модели не содержат `json`-тегов, SQL, типов `pgx` и зависимостей от сгенерированного пакета `api`.

Отдельные подпакеты для заказа, меню и заведения в MVP не создаются, чтобы не дробить небольшой домен и не усложнять зависимости.

## Сервисный слой
Бизнес-логика разделяется между тремя сервисами внутри одного пакета:

```text
internal/kitchen/service/
  establishments.go
  menu.go
  orders.go
```

В файлах определяются отдельные `EstablishmentService`, `MenuService` и `OrderService`. Один репозиторий может передаваться каждому сервису при сборке приложения.

Общая сервисная структура со всеми операциями не создаётся. Такое разделение не смешивает поиск и управление заведением, изменение меню и жизненный цикл заказа, но сохраняет простой единый пакет без дополнительных подпакетов.

Каждый сервис определяет рядом с собой узкий интерфейс необходимых операций репозитория: для заведений, меню и заказов. Конкретный `*repository.Repository` неявно реализует эти интерфейсы своими методами и передаётся сервисам при сборке приложения.

Сервисный пакет зависит только от собственных интерфейсов и моделей `domain`, а не от конкретного типа репозитория и `pgx`. В MVP моки репозитория не используются: чистые доменные правила проверяются unit-тестами, а связка HTTP, сервисов, репозиториев и PostgreSQL проверяется сквозными E2E-сценариями.

## HTTP-обработчики
Сгенерированный `api.StrictServerInterface` реализует одна структура `Handler`, которая получает три сервиса. Методы этой структуры разделяются между файлами по предметным областям:

```text
internal/kitchen/handlers/
  handler.go
  middleware.go
  establishments.go
  menu.go
  orders.go
  mappers.go
  errors.go
```

В `handler.go` находятся структура, конструктор и compile-time проверка реализации strict-интерфейса. Файлы заведений, меню и заказов содержат соответствующие HTTP-методы. `mappers.go` преобразует модели между `api` и внутренними слоями, а `errors.go` преобразует внутренние ошибки в ответы контракта.

Структура `Handler` не содержит бизнес-логику и не обращается к репозиторию напрямую. Она разбирает уже типизированный запрос, вызывает нужный сервис и формирует один из сгенерированных вариантов ответа.

`middleware.go` содержит транспортную обработку схем доступа из OpenAPI. Для партнёрских методов Bearer API-ключ хешируется, проверяется через `EstablishmentService`, а идентификатор заведения помещается в `context.Context`. Для просмотра и отмены заказа `X-Tracking-Token` хешируется, и в context передаётся только его хеш. Публичные методы не требуют секрета.

Исходные API-ключ и tracking token не передаются в сервисный слой и не записываются в логи. Отдельный `AuthService` и отдельный пакет middleware для этого объёма не создаются. Стандартные request ID и recovery middleware Chi подключаются при сборке HTTP-обработчика.

### Проверка запросов по OpenAPI
Перед strict server подключается `github.com/oapi-codegen/nethttp-middleware`. Он проверяет входящий запрос по спецификации: маршрут, параметры, обязательные заголовки и поля, типы и ограничения JSON-схемы.

Проверка security-требований выполняется через `AuthenticationFunc`, реализация которой находится в `handlers/middleware.go`. Ошибки схемы и авторизации обрабатываются собственной `ErrorHandlerWithOpts` из `handlers/errors.go`, поэтому клиент получает согласованные `validation_error` или `unauthorized`, а не стандартный текст библиотеки.

Для загрузки спецификации в настройках серверной генерации включается `embedded-spec`. OpenAPI встраивается в сгенерированный Go-код и не читается с файловой системы при запуске контейнера.

Runtime-валидация проверяет транспортный контракт, но не заменяет бизнес-правила. Актуальность цены, доступность блюда, принадлежность ресурсов и переходы статусов остаются в сервисном слое.

## Фоновая обработка таймаута
Автоматическое отклонение заказов с истёкшим временем подтверждения выполняется фоновым worker внутри процесса `kitchen`:

```text
internal/kitchen/worker/
  confirmation_timeout.go
```

Timeout worker работает в одной отдельной горутине и по настраиваемому интервалу вызывает операцию `OrderService`. Сервис применяет бизнес-правило, а репозиторий выполняет атомарное обновление просроченных заказов. Worker не обращается к PostgreSQL напрямую.

HTTP-сервер и timeout worker работают в разных горутинах одного процесса. `cmd/kitchen/main.go` координирует их запуск, передачу сигнала остановки и ожидание корректного завершения. Отдельный процесс или микросервис для timeout worker в MVP не создаётся.

## Конфигурация
Каждое приложение имеет собственный конфигурационный пакет:

```text
internal/
  kitchen/
    config/
      config.go
  establishment/
    config/
      config.go
```

Конфигурация загружается из переменных окружения средствами стандартной библиотеки, без отдельной конфигурационной зависимости. `config.Load()` применяет допустимые значения по умолчанию, проверяет обязательные параметры и возвращает готовую структуру.

Для основного сервиса настраиваются как минимум адрес HTTP-сервера, строка подключения к PostgreSQL, время ожидания подтверждения заказа, интервал проверки просроченных заказов и время корректного завершения.

Для примера заведения настраиваются базовый URL Авито.Кухни, Bearer API-ключ, интервал обработки заказов и время корректного завершения.

## Логирование
Для структурированных логов используется стандартный `log/slog`, без внешней библиотеки и отдельного logging-пакета. Каждое приложение создаёт свой `*slog.Logger` в `main.go` и пишет логи в stdout, чтобы Docker собирал их стандартным способом.

Логгер передаётся в HTTP-обработчики и фоновые workers. Request middleware записывает метод, маршрут, HTTP-статус, длительность и request ID. Workers записывают начало и результат обработки, а также ошибки внешних вызовов.

Доменный слой не зависит от логгера. Репозиторий и сервисы возвращают обёрнутые ошибки наверх, а окончательная ошибка логируется один раз на границе запроса или фоновой задачи. API-ключи, tracking token, контактные данные покупателя и другие секретные значения в логи не записываются.

## Генерация серверного API
Файлы генерации server-side обвязки находятся рядом со сгенерированным пакетом:

```text
internal/kitchen/api/
  generate.go
  oapi-codegen.yaml
  openapi.gen.go
```

`oapi-codegen.yaml` содержит настройки генерации моделей, Chi-сервера, strict server интерфейса и встроенной спецификации. `generate.go` содержит директиву `//go:generate`, которая читает корневой `api/openapi.yaml` и перезаписывает `openapi.gen.go`.

Версия `oapi-codegen` закрепляется в Go-модуле. Сгенерированный файл коммитится в репозиторий, поэтому для обычной сборки генератор не требуется. `openapi.gen.go` вручную не редактируется; после изменения контракта он обновляется командой `go generate ./...`.

## Генерация клиента Авито.Кухни
Пример заведения использует сгенерированный HTTP-клиент основного сервиса:

```text
internal/establishment/kitchenapi/
  generate.go
  oapi-codegen.yaml
  client.gen.go
```

Клиент генерируется из того же корневого `api/openapi.yaml` и коммитится в репозиторий. Через `include-tags: [Partner]` в него включаются только партнёрские операции. Пакет содержит транспортные модели и методы вызова Авито.Кухни, но не импортирует внутреннюю реализацию `internal/kitchen`.

Команда `go generate ./...` последовательно обновляет серверный пакет и клиент заведения. При необходимости каждый пакет можно сгенерировать отдельно.

Схемы данных в OpenAPI не называются по шаблону `<operationId>Response`, потому что такие имена генератор использует для служебных типов клиента. Поэтому результаты создания и отмены заказа называются `CreatedOrder` и `CancelledOrder`. Это правило применяется один раз в контракте и не требует ручных переименований при повторной генерации.

## Структура примера заведения
Пример заведения не предоставляет собственный входящий HTTP API, поскольку для выбранных бизнес-сценариев он не требуется. Приложение работает как фоновый процесс и обращается к партнёрскому API Авито.Кухни через сгенерированный клиент.

```text
internal/establishment/
  config/
    config.go
  kitchenapi/
    generate.go
    oapi-codegen.yaml
    client.gen.go
  worker/
    order_processor.go
```

У примера заведения нет собственных `handlers`, `domain`, `repository` и базы данных. В `worker/order_processor.go` находится небольшой цикл получения и обработки заказов. Дополнительные слои будут добавляться только при появлении реальной обязанности, которой нельзя дать понятное место в этой структуре.

Пример заведения автоматически демонстрирует успешный жизненный цикл заказа:

```text
pending_confirmation
-> confirmed
-> preparing
-> ready_for_delivery
-> delivering
-> completed
```

Worker с настраиваемым интервалом получает через партнёрский API заказы в активных статусах и переводит каждый заказ только на один следующий шаг за цикл. Текущее состояние хранится в Авито.Кухне, поэтому локальная база и восстановление собственного состояния после перезапуска заведению не нужны.

Пример заведения не симулирует отклонение, timeout и отмену заказа. Эти сценарии относятся к основному сервису и проверяются его тестами. Отдельные режимы поведения и управляющий HTTP API для демонстрационного заведения не создаются.
