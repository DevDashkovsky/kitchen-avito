# Авито.Кухня

MVP backend-сервиса, через который покупатель может выбрать блюда и оформить доставку без регистрации, а заведение может управлять меню и выполнять полученные заказы.

В репозитории находятся основной API-сервис, отдельный пример интеграции заведения, PostgreSQL, миграции Goose, OpenAPI-контракт и Docker Compose для общего запуска.

## Что реализовано

- поиск заведений по названию заведения или блюда;
- просмотр меню с категориями, ценами и доступностью;
- оформление, отслеживание и отмена заказа без аккаунта;
- проверка изменившейся цены и наличия перед созданием заказа;
- идемпотентное оформление по секретному ключу, включая одновременные повторы;
- закрытый API заведения для меню, приёма заказов и изменения статусов;
- связь блюд с каталогом заведения по внешним ID и восстановление этой связи через API;
- автоматическое отклонение заказа, если заведение не ответило за две минуты;
- отказ заведения после подтверждения, пока заказ не передан в доставку;
- отдельный сервис заведения, который проходит успешный lifecycle заказа;
- защита конкурентных изменений заказов и меню;
- cursor pagination для истории заказов заведения;
- liveness/readiness endpoints и единый JSON-ответ при panic/timeout;
- сквозные E2E-сценарии через настоящий HTTP API и PostgreSQL.

## Как я проектировал

Я начал не с кода, а с разборки задания и границ MVP. Сначала описал шесть бизнес-сценариев: успешный заказ, изменение цены или доступности, отклонение заведением, timeout подтверждения, отмена покупателем и обновление меню.

По этим сценариям составил две CJM, чтобы отдельно пройти путь покупателя и путь заведения. Затем определил пять сущностей: заведение, категория меню, блюдо, заказ и позиция заказа.

После сущностей спроектировал связи, ограничения, индексы и транзакции PostgreSQL. Следующим шагом зафиксировал OpenAPI: сначала покупательские методы, затем закрытые партнёрские методы и общие модели ошибок.

Когда контракт стал понятен, выбрал архитектуру Go-кода `handlers -> service -> repository`, вынес чистые модели и правила в `domain`, а транспортные DTO и интерфейсы сервера сгенерировал через oapi-codegen. После основного сервиса добавил отдельный сервис заведения, Docker Compose, линтер и E2E.

В конце код прошёл несколько циклов независимого review. По найденным замечаниям были исправлены конкурентные `PATCH` блюд, согласованность чтения меню, лимиты запросов, миграция demo data и изоляция E2E-окружения.

## Основные вопросы и решения

| Вопрос | Решение для MVP |
|---|---|
| Как отслеживать заказ без авторизации? | После создания вернуть случайный `tracking_token`, а в БД хранить только его SHA-256 хеш. |
| Что делать, если цена или наличие изменились? | Не создавать заказ, вернуть `409 Conflict` и актуальные данные изменившихся позиций. |
| Где хранить корзину? | На стороне web-клиента. Сервер получает только итоговый состав и заново проверяет его. |
| Что делать, если заведение не ответило? | Через две минуты автоматически перевести заказ в `rejected` с причиной `confirmation_timeout`. |
| Как защититься от гонки подтверждения, отмены и timeout? | Менять статус условным SQL `UPDATE`. Успешно завершается только первый допустимый переход. |
| Где проверять данные? | Понятные бизнес-ошибки формирует Go-код, а PostgreSQL защищает критическую целостность constraints и внешними ключами. |
| Как считать деньги? | Хранить значения целыми числами в минимальных денежных единицах, без `FLOAT`. |
| Кто отвечает за доставку и оплату? | Само заведение. Авито.Кухня хранит стоимость и статусы, но не управляет курьерами и платежами. |

## Схема БД

![ER-диаграмма](docs/diagrams/database-erd.svg)

[Исходник PlantUML](docs/diagrams/database-erd.puml) | [SQL-миграции](migrations)

В PostgreSQL пять основных таблиц: `establishments`, `menu_categories`, `dishes`, `orders` и `order_items`. Позиция заказа хранит снимок названия и цены блюда, поэтому последующее изменение меню не меняет уже созданный заказ.

Создание заказа и его позиций выполняется одной транзакцией. Конкурирующие переходы статуса защищены условным `UPDATE`, а меню читается из согласованного `REPEATABLE READ` snapshot.

## API

Полный контракт находится в [api/openapi.yaml](api/openapi.yaml).

| API | Возможности |
|---|---|
| Customer | список и поиск заведений, меню, создание заказа, статус и отмена по tracking token |
| Partner | управление категориями, блюдами и приёмом заказов, получение заказов и изменение статусов |

Список заказов заведения использует непрозрачный `cursor`, возвращаемый в
`next_cursor`. Служебные проверки доступны на `/healthz` и `/readyz`.

Покупательские методы не требуют аккаунта. Получение и отмена заказа защищены tracking token. Партнёрские методы используют `Authorization: Bearer <api-key>` и доступны только данным своего заведения.

## Повтор оформления после потери ответа

Перед первым `POST /api/v1/orders` web-клиент генерирует **32 случайных байта**
через криптографический генератор и сохраняет ключ вместе с телом запроса.
Например, в браузере:

```javascript
const bytes = crypto.getRandomValues(new Uint8Array(32));
const key = btoa(String.fromCharCode(...bytes))
  .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
// Сохранить {key, body} ДО отправки. При сетевом сбое повторить оба значения.
const response = await fetch("/api/v1/orders", {
  method: "POST",
  headers: {"Content-Type": "application/json", "Idempotency-Key": key},
  body: JSON.stringify(body),
});
```

Первое создание отвечает `201`, повтор с тем же нормализованным содержимым —
`200` с той же квитанцией: `tracking_token`, `total_minor`, `created_at`,
`status: pending_confirmation`. Это **результат создания**, текущий статус
читается через `GET /api/v1/orders/status` с `X-Tracking-Token`.
Повтор работает после смены меню, отмены заказа и перезапуска сервиса.

`tracking_token` совпадает с ключом: это секрет доступа к гостевому заказу.
Не передавайте его в URL, аналитику или логи. Сервер хранит только SHA-256
секрета и отпечаток запроса; ответы создания помечены `Cache-Control: no-store`.
Сервер проверяет формат ключа, а за его случайность отвечает клиент.
При потере и ключа, и token восстановить гостевой заказ нельзя.

Тот же ключ с другим валидным составом, ожидаемой ценой, заведением или данными
доставки возвращает `409 idempotency_key_reused` с пустым `conflicts`.
Идентичные позиции объединяются по прежним правилам, порядок позиций/JSON-полей
не влияет на сравнение. Пробелы по краям имени, телефона и адреса убираются;
`comment: null` и отсутствие комментария эквивалентны, пустая строка отличается.
Неверный или повторённый заголовок даёт `400` без раскрытия его значения.
Чтобы намеренно заказать ещё раз, используйте новый ключ. После изменения тела
при **неизвестном исходе** прежнего запроса сначала восстановите его результат:
новый ключ разрешает создать второй заказ.

Ключ хранится всё время существования заказа. Без заголовка сохраняется прежнее
поведение API, без защиты от повторов. В транзакции `READ COMMITTED` advisory lock
сериализует запросы с одним ключом; следующий отдельный запрос ищет сохранённый
результат до проверки текущего меню. UNIQUE по хешу token и атомарная запись
заказа/позиций/отпечатка защищают от дубликатов и частичного результата.

Миграция `00010` добавляет nullable `request_fingerprint`, старые заказы и tokens
сохраняются. Обновление MVP выполняется с остановкой старого процесса, затем
миграцией и запуском новой версии. Смешанный запуск старой и новой версии
не гарантирует идемпотентность. Откат `00010` сохраняет заказы и tokens,
но удаляет отпечатки и прекращает гарантию повтора; после повторного upgrade
прежний ключ даст конфликт, а отслеживание заказа останется доступным.

## Отказ после подтверждения

Заведение может отклонить заказ в `pending_confirmation`, `confirmed`,
`preparing` или `ready_for_delivery`. Например, если во время готовки сломалась печь:

```bash
curl -X PATCH http://localhost:8080/api/v1/partner/orders/42/status \
  -H "Authorization: Bearer $PARTNER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"status":"rejected","rejection_reason":"other","rejection_comment":"Сломалась печь"}'
```

Успех — `200` со статусом `rejected`, причиной и комментарием. Допустимые причины:
`out_of_stock`, `overloaded`, `delivery_unavailable`, `other`. Для `other` обязателен
непустой комментарий; предел комментария — 2000 символов. Покупатель увидит отказ
через обычный запрос статуса с `X-Tracking-Token`; стоимость и состав сохраняются.

После перехода в `delivering`, `completed` или `cancelled` отказ возвращает
`409 invalid_status_transition`. Отказ и передача в доставку конкурируют за один
переход: проигравшая операция получает `409`. Отменить заказ покупатель по-прежнему
может только до подтверждения.

Повтор `rejected` с валидным телом возвращает `200` с **первоначальными** причиной,
комментарием и `updated_at`, даже если прислали другую причину. Это не API исправления
причины: клиент должен читать сохранённый результат из ответа. Невалидное тело
возвращает `400` и при повторе. При двух одновременных отказах сохраняется причина
первой успешной записи; оба запроса могут получить `200` с этим результатом.

Таймаут подтверждения действует только на `pending_confirmation`. Если срок истёк
при попытке перехода, сервис записывает `confirmation_timeout` и отвечает `409`.
Повтор отказа для уже отклонённого по таймауту заказа возвращает сохранённую
служебную причину с `200`; назначить её партнёр не может. Старый подтверждённый
заказ допускает отказ независимо от времени его создания.

Ограничения MVP: используется общий статус `rejected`, поэтому этап отказа
отдельно не сохраняется. Неуспешная доставка, платежи и возвраты не моделируются.
Миграция БД не нужна. При обновлении замените процесс целиком: старый экземпляр
ещё запрещает новые переходы. При откате кода уже отклонённые заказы сохраняются.

## Внешние ID каталога заведения

Заведение может задать блюду `external_id` из своего каталога. Формат — 1–128
символов `A–Z`, `a–z`, `0–9`, `.`, `_`, `:`, `-`. Регистр и ведущие нули значимы:
`SKU-01` и `sku-01` различаются. Пробелы, пустая строка, Unicode и `null`
не принимаются. Для иных форматов интеграция должна выбрать устойчивое кодирование.

```bash
# category_id должен принадлежать заведению из PARTNER_API_KEY.
curl -X POST http://localhost:8080/api/v1/partner/dishes \
  -H "Authorization: Bearer $PARTNER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"category_id":1,"name":"Суп","price_minor":25000,"external_id":"SKU-01"}'

# Восстановление dish_id после потери ответа POST или локальной таблицы связей.
curl --get http://localhost:8080/api/v1/partner/dishes/by-external-id \
  -H "Authorization: Bearer $PARTNER_API_KEY" \
  --data-urlencode 'external_id=SKU-01'

# Однократная привязка старого блюда без внешнего ID.
curl -X PUT http://localhost:8080/api/v1/partner/dishes/42/external-id \
  -H "Authorization: Bearer $PARTNER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"external_id":"SKU-42"}'
```

Создание отвечает `201`, чтение и привязка — `200` с `Dish`. Поле `external_id`
опускается до назначения. Уникальность действует во всём заведении, включая
разные категории и недоступные блюда; у разных заведений одинаковые ID допустимы.
Повтор `POST` с занятым ID даёт `409 external_id_conflict`, даже при том же теле.
Он не переписывает блюдо: после неизвестного исхода сначала выполните поиск,
сверьте результат, а цену и наличие меняйте отдельным обычным `PATCH` по `dish_id`.
Повторённый query-параметр поиска возвращает `400`.

Привязка неизменяема: повтор `PUT` того же ID успешен без изменения `updated_at`;
другой ID для уже связанного блюда — `409 external_id_already_bound`, занятый
ID другого блюда — `409 external_id_conflict`. Снять привязку или переиспользовать
её для другого блюда нельзя. Обычный `PATCH` сохраняет привязку и не принимает
поле `external_id`. Старое создание без этого поля продолжает работать.

Для обработки заказа возьмите `order_items[].dish_id` и прочитайте
`GET /api/v1/partner/dishes/{dishId}` с partner key: получите **текущую** привязку.
Её можно кэшировать. Если внешний ID назначен после оформления, он будет доступен
и при разборе старого заказа. Название и цена в позиции заказа остаются снимком
на момент оформления; не заменяйте их текущими данными блюда.

Внешний ID доступен только через закрытые операции блюда. Публичные меню,
заказы и общий ответ `GET /partner/menu` сохраняют прежнюю форму. Знание ID
не даёт доступ без ключа заведения; чужое и отсутствующее блюдо дают одинаковый
`404`. Строгие потребители, проверяющие закрытый ответ `Dish` по прежней схеме
с `additionalProperties: false`, должны обновить контракт/клиент.

Миграция `00011` заполняет владельца блюда из категории и добавляет составной FK
и `UNIQUE(establishment_id, external_id)`. Старые блюда остаются без внешней
привязки. Выполняйте обновление с остановкой приложения: старый процесс не задаёт
новый обязательный `establishment_id` при записи. Откат включает схему и приложение;
`down` сохраняет блюда и заказы, но **удаляет внешние привязки**. Перед откатом
сохраните нужные соответствия; повторный `up` их не восстановит. Откат одного
бинаря без схемы не поддерживается.

## Запуск

```bash
docker-compose up --build
```

API будет доступен на `http://localhost:8080`. Схемные миграции применяются
автоматически, после чего Compose отдельно загружает локальные demo-данные.
Публичный demo API-ключ не входит в production-цепочку миграций. Вместе с
сервисом запускается demo-заведение с API-ключом `demo-partner-key`, двумя
категориями и тремя блюдами.

Основные таймауты можно переопределить через `CONFIRMATION_TIMEOUT`,
`TIMEOUT_SCAN_INTERVAL`, `REQUEST_TIMEOUT`, `HEALTH_CHECK_TIMEOUT` и
`SHUTDOWN_TIMEOUT`.

Остановка:

```bash
docker-compose down
```

Если используется Compose v2, команды можно запускать как `docker compose ...`.

## Проверки

```bash
make test
make test-race
make lint
make test-e2e
make test-postgres  # локальный PostgreSQL, без Docker
make check-generated
```

`make test-e2e` поднимает отдельное временное Compose-окружение без worker-а заведения, проверяет реальные HTTP-сценарии и удаляет только свои контейнеры и volume.

`make test-postgres` требует PostgreSQL 16+ (`initdb`, `pg_ctl`, `psql`,
`createdb`), Go, Python 3 и Bash в PATH. Создаёт отдельный временный кластер
с приватным Unix socket, устанавливает Goose v3.27.2 во временный каталог,
проверяет SQL/HTTP-сценарии с race detector, upgrade/rollback миграции,
затем запускает прежние E2E, повтор оформления и поиск внешнего ID через реальный
перезапуск API. Для новой миграции внешних ID используется отдельная временная БД;
проверки миграции идемпотентности закреплены на версиях 9/10.
Первый запуск может потребовать сеть для Go-модулей. Кластер и процессы
удаляются по завершении; пользовательская БД не используется.
Docker Compose при этом не проверяется — для него остаётся `make test-e2e`.

Для повторной генерации серверных типов и клиента:

```bash
go generate ./...
```

## Упрощения MVP

- покупатели считаются гостями, связь заказа с аккаунтом Авито не хранится;
- один заказ содержит блюда только одного заведения;
- меню небольшое и возвращается целиком без пагинации;
- уведомления работают через polling, без WebSocket, SMS и push;
- изображения, платежи, курьеры, удаление данных и история статусов не реализованы;
- без `Idempotency-Key` повторный `POST` может создать второй заказ; новый клиент должен использовать ключ;
- монетизация не входит в MVP. Возможное развитие: агрегировать суммы завершённых заказов и рассчитывать процент комиссии заведения.
